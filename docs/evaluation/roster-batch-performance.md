# 参试名单批量性能基准（Issue #39）

## 范围与可比性

2026-10-22，在同一台开发机、同一独立 PostgreSQL 16.15 测试库上串行执行。对照为 main `84933c9a8f9a60654d49f96da34b0d3ba6ce995d`；优化仅改变名单来源装配、批量写入及事务预算，不改变名单、授权或冻结协议。每个规模使用两个独立 fixture，完整执行创建→替换→冻结→更正，再冻结并分页全量回读。没有并行运行完整回归干扰这两组基准。

所有身份与材料均为合成数据。八班共享同一场次与卷版；A/B 场景显式建立两个本场次绑定，各班交替分配，不复制题目。样本与参考资料、历史评测结果分离。

原审查的 16052 次 SQL / 12.57s 是另一次观测，不当作本次重测值。用户授权数据及开发库未用于测试。两轮结果不是容量 SLA，也不能代表真实学校负载。

原始聚合记录见 [JSON 证据](roster-batch-issue39.json)。数据包含每次结果，不只保留最快值。权限检查遍历当前 Grant，fixture 使用随机 UUID，因而授权部分 SQL 数可能有差异；权限算法没有改动。正文比较中位数，同时列出每次计数。

## 测量口径

- `sql_executions`：SQLAlchemy `before_cursor_execute` 看到的应用客户端执行次数；监测连接使用另一 Engine，不混入计数。不是 PostgreSQL 触发器内部 SQL 次数，也不等于 TCP 包数。
- 写入显式采用每批最多250条的 multi-VALUES SQL；不是把2000次 executemany 隐藏成一个事件。测试记录 `insert_executemany=false`，单句绑定参数不超过5000。
- `cursor_seconds`：客户端执行 SQL 的墙钟时间之和，包含网络、数据库执行、触发器及锁等待，不能称为数据库纯 CPU 时间。
- `assembly_seconds`：新版纯 `snapshot_rows()` 装配时间；旧版没有独立装配阶段，不补造对照值。其余非游标、非提交时间还包含校验、SQL 构建和调度，不能全部归为数据转换。
- `commit_seconds`：实际 AsyncSession.commit 的耗时；总耗时包括当前授权、来源校验、写入、审计与提交，不含 fixture 造数、模型构造和之后的分页检查。
- `lock_wait_samples` / `sampled_lock_seconds`：独立连接约每20ms采样目标 backend 的 pg_stat_activity，后者是粗略积分，不是精确锁等待计时。无争用基准未观测到 Lock 样本，不代表生产不会等待。确定性竞争测试另外用 Event/Barrier 和 pg_locks 验证。
- `rss_peak_bytes` / `rss_peak_delta_bytes`：采样 Linux 当前进程 RSS，包含 Python、原生库及既有堆。可能漏掉短峰值；零增量不代表零分配，不是每事务独占内存或数据库 backend 内存。来源数最多2000，单批最多250，响应仍限每页100。

## 数据库内部开销

另外执行真实写入的 `EXPLAIN (ANALYZE, FORMAT JSON)`，不是只看执行计划：2000条快照分8批，`protect_roster` 调用2000次，所有外键触发器仍执行。服务器 Execution Time 与触发器累计耗时见 JSON 的 `server_profile`，与普通基准分开记录。

触发器内部 SQL 次数未测量，不以客户端 SQL 次数替代。保留的逐行可信来源校验和人数 count 检查仍有服务端成本。后续如确需优化应单独审查数据库不变量，不在本轮禁用触发器或修改历史迁移。

## 可复跑方式

先按[验证指南](../development/validation.md)配置独立 `_test` 数据库与独立 S3 测试桶；TEST_DATABASE_URL 必须不同于开发库。数据库夹具会迁移、清理该测试库，因此不得指向任何开发或业务库。凭据使用本地安全环境注入，不写入命令历史。下面只写聚合结果，没有姓名、学号、连接串或 Token：

```bash
ROSTER_BENCHMARK_REPEATS=2 \
ROSTER_BENCHMARK_LABEL=reviewed-build \
ROSTER_BENCHMARK_OUTPUT=/tmp/huipi-roster-benchmark.jsonl \
ROSTER_TRIGGER_PROFILE_OUTPUT=/tmp/huipi-roster-trigger-profile.json \
uv run pytest -q -s tests/integration/test_exam_roster_batch.py
```

JSONL 使用追加方式，应为不同代码版本选择不同输出文件；不得混用历史标签。测试要求每个业务操作客户端执行不超过256次、插入不是 executemany、参数不超5000，并检查2000条全量回读与稳定 Participation 数量。耗时不设脆弱的机器相关断言。

## 安全、并发和残余风险

来源按 Student ID、Enrollment ID、Class ID、SessionPaper ID、PaperVersion ID 各自有序 SHARE 锁定；同场次首先持有 Session UPDATE，查 Participation 与写入间不会被另一正常场次写操作插入同身份。不同场次可共享同一批学生及锁卷，只创建各自 Participation，不复制卷版。Core 查询直接取当前行，避免 ORM 身份映射缓存旧标签。

没有 ON CONFLICT DO NOTHING；意外唯一约束冲突使整笔请求回滚。快照触发器、复合外键、不可变规则、单 Grant 授权、原子 current 切换均保留。锁和业务写入一直保留到同事务审计及 COMMIT。权限撤销只需等已授权在途事务结束，之后新请求和幂等重放重新检查当前授权。

PostgreSQL 16 没有 transaction_timeout。本轮保留单句8秒限制，新增默认5秒 lock_timeout；应用协作式业务预算默认60秒（可配置15–300秒），覆盖事务建立、授权、写入、审计和COMMIT。该默认值高于旧2000人基准中最慢约13秒操作的四倍，并为优化后正常操作留下余量，不按本机最快值设超时。环境变化需重新测量与调整。

超过提交前预算返回503 `roster_operation_timeout` 并回滚；锁/数据库故障返回503 `roster_operation_unavailable`；已经开始COMMIT后的超时保守返回 `roster_commit_outcome_unknown`，同request_id按当前权限恢复，不自动重试。回滚另有5秒清理窗口；协作取消和驱动清理不等于操作系统级硬终止，不能承诺所有网络故障都在严格65秒墙钟内结束。外部取消仍传播，已执行的批次全部回滚。
