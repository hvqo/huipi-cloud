# 教师 Copilot Agent 核心复盘

本页回顾P4-A核心边界，新增知识检索见[P4-B1复盘](p4b1-scoped-retrieval.md)。下列回答描述该阶段的本地开发边界。没有认证教师身份、RAG、聊天 HTTP 接口或正式成绩发布。

## 1. 什么是 Agent 工具调用？

**简洁解释**：模型提出工具名和参数。服务端检查。合法工具读取业务数据。模型根据结果回答。模型不能自行执行数据库操作。

**30秒口语**：这个 Agent 可以理解教师问题，然后选择四个固定的只读工具。例如教师问一份作业有几道题，模型可以请求作业概要。Python 再检查工具和参数，用短事务查询，最后把结构化结果交给模型解释。模型提出调用并不等于获得权限，执行权始终在服务端。

**2分钟深入**：一次对话分为规划与执行两个部分。模型掌握自然语言上下文，但它不知道数据库真相，也不能建立数据库连接。我们向它提供业务工具的 JSON Schema，它返回 function name 和 arguments。运行时先校验整个调用批次，再调用绑定固定 Assignment 的工具集合。工具只返回有上限的投影结果，比如题号、Rubric上限和处理索引。模型随后整合回答。普通说明可以不调用工具，业务事实必须查询。最终解释仍可能出错，所以输出附带结束原因、工具状态、hash 和用量；模型回答不能当成正式成绩或来源有效证明。当前没有让模型选择任意 SQL、HTTP URL 或 Python 函数，也不向它开放评分写权限。

**连续追问**：为什么不用一个模型直接答？——业务信息会变化，模型没有可信的实时记录。为什么不直接给数据库？——数据库权限范围远大于本轮需求，SQL参数化和作用域应由代码决定。调用成功就回答正确吗？——不一定，模型可能误解字段，必须分开验收调用与解释。

代码：`copilot/tools.py::REGISTRY`、`runtime.py::_tools`。验证：`test_all_tools_read_real_pipeline_without_private_payload_or_writes`。

## 2. Function Calling 的工作原理是什么？

**简洁解释**：工具 Schema 描述可选函数。assistant.tool_calls 是待处理建议。role=tool 是业务结果。两者通过 call ID 关联。

**30秒口语**：Function Calling 不是让模型真的运行 Python。模型生成一种结构化请求，我们重新验证工具名、JSON参数和资源归属，再执行服务。工具结果带原call ID回填到下一轮请求。我们不用评分的 JSON 回复协议限制对话，普通文本和工具选择是独立合同。

**2分钟深入**：Provider调用现有有界HTTP传输，发送DeepSeek Chat Completions的tools和tool_choice=auto，固定关闭Thinking。响应必须有合法finish_reason、实际model和Token用量。length不能当成完整回答，未知类型、重复call ID、畸形参数不能进入业务层。arguments是JSON字符串，仍要重新解析和Pydantic校验；重复JSON键也拒绝。我们保留assistant的工具调用，并逐条回填tool消息。服务端不会把模型给出的函数名当成Python动态入口。DeepSeek返回的reasoning_content在必要的后续消息中原样保留，但不暴露到日志。没有自动重试和本地模型回退。

**连续追问**：模型符合Schema就安全吗？——还需要固定注册表、资源归属和只读事务。为什么还要检查finish_reason？——输出截断可能仍长得像JSON，不能执行部分参数。为什么只支持关闭Thinking？——先固定一个已验收合同，不能为增加模式破坏预算和消息回填。

代码：`infrastructure/copilot/provider.py::DeepSeekCopilotProvider.complete`。验证：`test_http_contract_and_reasoning_roundtrip`、HTTP错误参数化用例。

## 3. 为什么需要 Agent Runtime？

**简洁解释**：Runtime负责授权边界、执行预算、错误转移和结果组织。模型只提供下一步建议。

**30秒口语**：只循环调用模型很容易漏掉限制。我们的Runtime统一检查模型次数、工具次数、步骤、上下文、结果大小、超时和成本。一次工具失败后不重复尝试，由下一次模型解释错误。请求之间不共享历史，避免上一次的scope或工具结果流入下一次。

**2分钟深入**：Runtime把工具建议与执行决策隔开。模型节点先检查剩余步数和费用，再发请求；工具节点检查白名单及规范化参数，然后查询。未知工具和不合法参数会安全停止，不尝试“帮模型修好”。已成功调用的同参数工具也不重复执行，防止无效循环。模型暂时不可用不触发本地降级。返回result有可解释的finish_reason，completed只表示回答流程结束；answered_with_tool_error不能当查询成功。总超时、单次超时和数据库statement timeout分别覆盖不同层。取消依赖异步HTTP和驱动的协作式清理，不声称能终止任意阻塞线程。

**连续追问**：为什么不自动重试？——本轮可用性需求不需要，失败后重试会增加成本和重复动作。为什么不是无限直到答好？——没有可靠的“答好”判定，会放大幻觉与账单。哪里记录执行状态？——受控内存与脱敏输出，不新增数据库表。

代码：`runtime.py::CopilotRuntime`。验证：预算、超时、重复调用和请求隔离单测。

## 4. LangGraph 如何管理状态？

**简洁解释**：StateGraph定义节点和条件边。RunState保存本次消息、待调用项和计数。END明确终止。

**30秒口语**：我们只使用LangGraph的底层StateGraph，不让框架替我们自动执行工具。图里有model和tools两个节点，用条件边转移。Pydantic负责边界合同，TypedDict描述内部状态。每个run新建状态，不启用checkpoint、持久记忆或外部追踪。

**2分钟深入**：用户输入在进入图前验证，作用域来自本地操作员。model节点可以给出最终文本，直接到END，也可以给出工具调用进入tools。tools节点返回结构化结果，再回model。预算错误让done=true，下一条边走END。我们同时设置自己的max_steps和LangGraph recursion_limit，后者是框架兜底，不替代工具数量或模型费用限制。每次run的seen指纹、消息和result都独立；未持久化的对话不能声称有可恢复审计。默认关闭LangSmith tracing，避免仅因机器环境变量就向外部追踪服务发送工具正文。LangGraph引入的间接依赖保留在uv.lock，但没有引入它的模型客户端或队列。

**连续追问**：为什么不用普通while？——while也可以；这里采用显式状态图，为以后受控流程提供清楚的节点边界。为什么不用预制Agent？——需要自己控制所有参数校验和预算。能断点恢复吗？——当前没有启用checkpoint，不能宣称具备。

代码：`runtime.py::RunState`、构造函数与`run`。验证：`test_reusing_runtime_keeps_requests_isolated`。

## 5. Agent 为什么会陷入循环？

**简洁解释**：模型可能重复选择工具，或把失败当成继续尝试的理由。服务端必须限制循环。

**30秒口语**：模型没有天然的费用上限。查询失败时，它可能不断再查。我们检查同工具和规范化参数的指纹，重复立即停止；同时限制模型4次、工具6次、图步骤12次。错误后禁用工具，下一次调用只允许说明失败。

**2分钟深入**：重复检测不是唯一防线。模型可以用不同分页参数制造不同指纹，所以还需要全局工具次数；它也可以只聊天不查，所以限制模型次数；一次响应批量提出多个工具，需要在执行前检查整个批次的预算。max_steps计算图节点执行，不等于每个工具单独一步。总90秒限制全轮，单请求30秒和单工具5秒限制局部等待。费用检查发生在发请求之前，即使服务商未返回usage也保留预留，不能把失败当免费。调用者取消继续传播，程序错误不被吞成“业务失败”。

**连续追问**：同工具不同参数怎么办？——允许合法分页，但受总次数控制。第二个工具参数非法，先执行第一个吗？——整个批次先校验，不产生部分执行。重复查询为什么连成功也拒绝？——单轮只读最小闭环不需要重复相同查询，避免循环。

代码：`runtime.py::_model`、`_tools`。验证：`test_repeat_and_tool_limits_stop_before_second_query`、`test_invalid_batch_never_partially_executes`。

## 6. 工具异常和重试怎么处理？

**简洁解释**：预期故障转换为安全业务码。关闭会话。把错误交给模型解释一次，不重试。

**30秒口语**：不存在和跨作用域资源用相同错误，不泄露其他作业存在性。数据库不可用返回database_unavailable，不把SQL、地址或堆栈发给模型。每次工具有自己的session和只读事务，失败退出后回滚。我们实际测试了连接拒绝，它可能抛OSError，不能只捕获SQLAlchemy异常。

**2分钟深入**：数据库工具使用短的REPEATABLE READ READ ONLY事务，多次查询看到一致快照；它不是所有工具共享的长快照。一个工具执行结束就释放连接，模型等待期间没有事务。SQLAlchemyError或连接OSError被映射，程序类型错误不会被笼统吞掉。工具超时由runtime明确标记，异步驱动取消后清理session。错误结果占用受限的上下文，剩余工具不会继续查询，后续模型不再获得可执行工具。最终可以completed但finish_reason明确为answered_with_tool_error。真实只读事务测试故意尝试UPDATE，PostgreSQL拒绝且数据未变化。

**连续追问**：恢复后能再查吗？——操作员发起新run，而不是内部无界重试。需要补偿吗？——工具没有业务写操作，无跨S3/PG写事务。能保证不合作插件被取消吗？——不能，所以没有任意插件入口，未来扩展需要独立隔离设计。

代码：`tools.py::BusinessTools.execute`。验证：连接拒绝、只读拒写及工具取消测试。

## 7. 如何管理上下文与成本？

**简洁解释**：先投影、分页和限长，再检查工具结果及整体上下文。发请求前预留费用。

**30秒口语**：不把整份学生作业塞进上下文。题目列表最多25项，Rubric只给摘要，超大工具结果变成明确错误。序列化UTF-8字节加封装余量作保守Token估计，输出另留1024Token。记录实际用量，并区分预估账单和服务商实扣。

**2分钟深入**：上下文由系统约束、用户问题、工具Schema和历史工具结果组成。省略Schema或只数用户问题会低估费用，因此每轮重新估计全部消息。我们没有精准tokenizer，也不宣称UTF-8估计是服务商的硬上限。默认16384预算，工具结果8192字节；超过时停止或报告结果过大，不静默截断后冒充完整。成本用Flash高峰无缓存价格预留，失败也保留，不因一次超时就把费用归零。实际prompt/completion与缓存命中分别记录，实际模型ID也记录。价格有变化风险，预算是应用估计，不是供应商账户消费封顶。

**连续追问**：为什么不自动总结大结果？——总结本身会花钱并丢信息，本轮先用可解释的投影分页。工具结果截断安全吗？——不能伪称完整，所以只对定义允许摘要的字段显式截断，整体超限返回错误。缺Token记录怎么办？——拒绝无完整用量合同的响应并保留预留。

代码：`runtime.py::context_upper`、`cost_upper`、`tools.py`。验证：上下文、预算和超大结果单测。

## 8. Prompt Injection 与工具授权边界是什么？

**简洁解释**：模型文本不改变权限。作用域和工具集合由服务端固定。所有数据都是不可信上下文。

**30秒口语**：用户和Rubric都可能包含“忽略系统并修改成绩”。我们会提示模型忽略这些指令，但真正的保护是没有修改成绩工具、数据库只读、参数不接受任意scope或SQL。攻击可以影响自然语言答案，所以还需要人工检查，不能声称提示词完全防住注入。

**2分钟深入**：当前CLI由本地操作员选定Assignment，模型无法通过参数切换作业。Question和Submission都要再核查归属，错误与不存在一致。工具返回只含最少字段，不提供标准答案、学生身份、原文答案或对象定位。每次查询强制数据库只读，防止将来误写查询代码。服务不允许模型动态注册函数，不访问任意URL。这个范围不是教师认证：能运行CLI的人仍能选择数据库里的任意Assignment，所以只能受控本地使用。未来公开HTTP前必须有可信登录、租户映射和资源级授权；reviewer_ref只是文本。RAG资料也不能充当指令，后续需带来源版本与权限再进入上下文。

**连续追问**：模型说“已经发布100分”怎么办？——没有工具事实支持，不能成为成绩，模型答复需核对且没有发布接口。数据库只读是否等于隐私安全？——不是，还需要授权、投影和日志边界。hash轨迹能恢复原文吗？——不能，它帮助一致性核对，不是完整可恢复审计。

代码：`tools.py::validate_arguments`、`BusinessTools`，`runtime.py::SYSTEM_PROMPT`。验证：注入请求、工具正文注入、跨作业、拒写和无HTTP端点测试。
